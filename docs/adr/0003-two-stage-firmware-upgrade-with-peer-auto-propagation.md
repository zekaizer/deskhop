# Two-stage firmware upgrade with peer auto-propagation

The device flashes itself in two stages and propagates the new image to its peer automatically. Each board's flash is split into a **running** slot (slot 0) and a **staging** slot (slot 1, 256 KB = 1024 × 256-byte pages). The user copies a UF2 file to one board only; that board writes the image into its own staging slot, verifies the CRC32 in the trailer sector, swaps slots on reboot, and the next heartbeat exchange detects the version mismatch on the peer and auto-propagates the new running firmware over UART page-by-page (`send_fw_byte` reads from running, `receive_fw_byte` writes to peer's staging). The peer then swaps and reboots, leaving both boards on the same version.

Chosen over the obvious alternative — "user must flash both boards manually" — because the device presents itself as a single USB target (DESKHOP), and exposing the dual-Pico topology to the user would defeat the appliance feel. Chosen over a single-slot in-place flash because the running slot must remain executable while the new image is being received over UART (which can take seconds at 115200 baud), and we need a CRC verification step before committing.

The cost: code is constrained to ~half the flash budget (the other half is reserved for staging); both boards are forced onto the same firmware version (no per-board variants); the UART protocol must carry firmware bytes (`FirmwareUpgrade`, `RequestByte`, `ResponseByte` packet types) alongside HID traffic; and the upgrade state machine adds non-trivial complexity (`fw_upgrade.rs`, debug-only Board-B auto-pull at matching version with mismatched CRC, address-sequence validation, page accumulation, indicator blinking every 4 KB). The trade-off was deemed worth it for the "copy one file, both update" UX.
